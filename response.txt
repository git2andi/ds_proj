## 1. Executive Summary

Your current system is already beyond a simple “LLM writes a chat” prototype. It has a meaningful separation between orchestration, persona generation, simulator turns, consensus detection, moderation, turn selection, logging, and LLM access. The current design also correctly recognizes that group decision dialogue needs phases, private belief states, turn-taking, moderation, and explicit narrowing rather than a single unconstrained prompt. This matches the project description in `CLAUDE.md`: the intended system is a controlled decision dialogue where plausible group behavior emerges from state, personas, turn logic, and prompts, not from free-form generation alone. 

The main problem is that the architecture is still heuristic-heavy. Many of the right concepts exist, but they are represented too weakly: phases are mostly procedural labels, consensus is mostly regex/string matching plus LLM fallback, addressee handling is shallow, and the dialogue history is still mainly a `list[str]`. For a scientifically grounded simulator, this is not enough. You need a structured dialogue state with explicit per-turn metadata: speaker, addressee, reply target, dialogue act, option stance, question obligations, phase evidence, and per-option support/opposition/ambiguity.

The largest technical issue is not simply “bad prompting.” It is missing state. Some prompt bloat exists, but many repetitive or stubborn behaviors come from the fact that the simulator often has no precise conversational obligation other than “say another negotiation turn.” `CLAUDE.md` already states the right diagnosis: repetition is usually caused by missing dialogue state, and the correct fix is to create obligations such as answer this person, explain this rejection, test this compromise, or name one drawback of your own option. 

The current architecture should be substantially refactored, not merely patched. The core idea should become:

state tracker → turn/addressee policy → dialogue-act planner → compact LLM realization → stance/phase/consensus update → moderator policy → logging/evaluation.

That means the LLM should mostly realize planned behavior in natural language. It should not be responsible for repeatedly re-inferring the entire dialogue state from a large text prompt.

A likely cause of excessive stubbornness is that low agreeableness, high neuroticism, rejected options, skepticism nudges, and emergence-phase opposition prompts combine into a much higher blocker rate than intended. Low agreeableness should mostly affect disagreement style, not the probability of being a hard blocker. Hard blocking should be an explicit rare dialogue-level variable, capped by config, for example “0–10% of dialogues contain one true blocker,” not an emergent side effect of several independent heuristics.

The most important next step is diagnostics before behavior changes. Add structured traces and run a batch baseline. Measure stubbornness frequency, force-close rate, participation balance, phase progression, addressee/question-answer compliance, stance changes, invented facts, and token usage per component. Without this, every prompt or threshold change will remain guesswork.

## 2. Current Architecture Understanding

The current project is a single-topic multi-party decision simulator. For each topic, it generates four concrete options, creates simulated participants with Big Five traits and private beliefs, runs a phased group discussion, checks for consensus, intervenes with a moderator when needed, and logs transcripts plus structured CSV rows. This is directly described in `CLAUDE.md`: `main.py` creates the orchestrator, the orchestrator generates options, `PersonaBuilder` creates personas, `Simulator` produces turns, `TurnManager` selects speakers, `ConsensusDetector` checks agreement, `ModerationEngine` intervenes, and `DialogueLogger` writes outputs. 

The current high-level architecture is:

`main.py`
Entry point. Handles interactive mode, batch mode, persona override files, participant count, orchestrator creation, persona creation, simulator wrapping, and execution.

`config_loader.py`
Loads `config.yaml` once and exposes a global `cfg` object. This is the correct direction for your “all numeric parameters in config” requirement, but the current codebase still has many behavior-controlling numbers outside config. 

`orchestrator.py`
Central runtime coordinator. It owns the `DialogueState`, generates options, builds the opening moderator messages, runs the main loop, updates phase, tracks leading option, calls speaker selection, calls simulators, checks consensus, calls moderation, tests compromise, handles confirmation, and eventually closes or force-closes. The file header itself describes it as coordinating setup, state, main loop, and conclusion. 

`persona.py`
Defines the Big Five trait names, communication field `response_length`, `Persona`, `AgentBeliefs`, and `PersonaBuilder`. The stated pipeline is: sample Big Five traits, enforce diversity, call the LLM once per participant for backstory/goal, call the LLM once per participant for beliefs, then assemble and save personas. It also documents the setup call count as `1 options + 1 roles + N persona concept + N beliefs = 2N + 2`. 

`simulator.py`
Wraps a `Persona` and generates one turn by building a prompt and calling the LLM. It injects persona, beliefs, options, recent history, phase instructions, interaction instructions, position discipline, forbidden openers, and repetition controls. The file explicitly states that it formats turn prompts, strips artifacts, builds belief blocks, provides position discipline, and tracks repeated phrases/openers. 

`turn_manager.py`
Selects speakers. It uses phase coverage, direct address, pending question target, trait-based weights, recent-speaker penalties, primary participant boost, and repetition pressure. Its current addressee detection scans the most recent participant line for name mentions and question marks. 

`consensus.py`
Implements multi-tier consensus detection: soft agreement language, regex vote extraction, reduced opposition in emergence, and LLM fallback every N turns. The detector only runs after everyone has spoken at least twice. 

`moderation.py`
Decides when and how the moderator intervenes. It owns narrowing triggers, escalation levels, speculative-loop detection, outlier detection, stall handling, and LLM moderator lines. 

`prompts.py`
Central registry for many prompt templates: option generation, role assignment, persona concept, agent beliefs, simulator turn, consensus check, and moderator prompts. This is the right target file, but not all LLM-facing prompt text currently lives here. `simulator.py` still constructs important LLM-facing strings such as phase instructions, narrowing instructions, interaction instructions, position-discipline text, and skepticism nudges before passing them into `prompts.sim_turn`. 

`llm_client.py`
Provider abstraction over Gemini, Groq, and a university/local endpoint. It also tracks last-call and session token usage. The design is useful, but the current token logging is not yet granular enough to identify which prompt component causes most cost. 

`logger.py`
Writes transcript, CSV rows, persona JSON, and token logs. Current CSV columns include phase, speaker, selected reason, last addressed, pending question target, repetition pressure, tokens, and persona traits. This is a good start but does not yet log dialogue acts, option stances, addressee/reply graph, consensus evidence, phase evidence, or prompt component costs. 

`utils.py`
Shared regex/string helpers for vote extraction, option mention extraction, current votes, recent participant lines, and related functions. It is useful but still fundamentally text-pattern based.

## 3. End-to-End Generation Workflow

The current workflow is roughly:

1. `main.py` parses user input or a scenario file.
2. It determines participant count from config or persona override length.
3. It creates an `Orchestrator(topic, moderator_style)`.
4. The orchestrator immediately calls `_generate_options()`, which sends an LLM prompt to generate four options and an opening question.
5. The orchestrator builds the initial moderator history containing topic, options, and opening question.
6. `PersonaBuilder` creates participant names, roles, Big Five traits, backstories, goals, and private beliefs.
7. Each `Persona` is wrapped in a `Simulator`.
8. The orchestrator initializes `ConsensusDetector`, `ModerationEngine`, logger, and dialogue state.
9. The main loop begins.
10. `TurnManager.select_speakers()` picks one or more simulators.
11. Each selected simulator builds a turn prompt and calls the LLM.
12. The generated turn is appended to `history`.
13. Orchestrator updates last addressed, pending question target, repetition pressure, current leading option, vote changes, and phase.
14. `ConsensusDetector.detect()` checks whether agreement has emerged.
15. `ModerationEngine` may trigger narrowing, clarification, outlier handling, compromise testing, or force-close logic.
16. If consensus is detected, the system asks for confirmation and then closes.
17. If the hard ceiling is reached or escalation expires, the system force-closes or logs failure.
18. Logger writes transcript, CSV, personas, and token totals.

This workflow is coherent as a prototype. The weakness is that most “state” is inferred repeatedly from raw transcript strings. For example, current votes are extracted from recent text; addressee is inferred from name mention in one recent line; consensus is inferred from phrases; phase is updated from procedural counters. This is exactly where the system becomes brittle.

The current system has the correct major objects, but the wrong central data model. A realistic multi-party simulator should not treat the transcript as the primary state. It should treat the transcript as the rendered surface of a structured interaction state.

## 4. Module-by-Module Analysis

### `main.py`

`main.py` is mostly fine as an entry point. It supports interactive mode, batch mode, and persona override JSON. It also separates setup token accounting from dialogue token accounting by resetting the LLM session after persona creation. That is useful.

The main weakness is that setup is tightly coupled to orchestrator construction. Creating the `Orchestrator` already triggers option generation. That makes it harder to test setup stages independently. A cleaner design would have an explicit `DialogueFactory` or `SimulationBuilder`:

`topic → options → personas → initial state → orchestrator.run()`.

This is an engineering inference, not a paper claim.

### `config_loader.py`

The config loader is simple and acceptable. It loads YAML once and exposes `cfg`. The project goal says all numeric behavior parameters should live in config; `config_loader.py` supports this direction. 

However, the codebase does not currently satisfy the rule. Many numeric thresholds and weights remain inside `turn_manager.py`, `simulator.py`, `consensus.py`, `moderation.py`, `orchestrator.py`, `utils.py`, and `llm_client.py`.

### `orchestrator.py`

This is currently the central control file. It does too much. It owns option generation, phase transitions, participant rounds, vote tracking, consensus calls, moderator interventions, confirmation, compromise scoring, force-close scoring, and closure. 

The `DialogueState` dataclass is useful but too flat. It stores fields such as phase, preferred option, current leading option, last addressed, pending question target, rejected options, vote changes, emergence flags, and compromise flags. What is missing is more important than what is present:

No structured turn objects.
No explicit addressee list per turn.
No explicit reply-to link.
No dialogue-act label.
No per-option stance state.
No unresolved question objects.
No per-option blocker/condition tracking.
No phase evidence.
No distinction between public transcript evidence and private beliefs.

The current orchestrator should be split. Keep it as the high-level runner, but move state updates, turn selection, dialogue-act planning, consensus, phase detection, and moderator policy into separate modules.

### `persona.py`

This is one of the stronger modules conceptually. It correctly separates Big Five traits from `response_length`, and it correctly stores private beliefs separately from public dialogue. `CLAUDE.md` also states that private beliefs guide coherence, but decisions must be visible in the transcript; the moderator cannot select an option purely because hidden beliefs say it is acceptable. 

The biggest problem is distributional. If traits are sampled uniformly from 1–5, extreme low agreeableness and high neuroticism will occur too often. In real use, low agreeableness should not mean “blocks consensus.” It should mostly mean more direct disagreement style, less soft validation, and slower concession. A true hard blocker should be a rare explicit latent variable.

Another issue is belief generation. The prompt asks for 2–3 acceptable options, but the code needs post-hoc validation. A prompt instruction alone is not enough. If a persona gets only one acceptable option and multiple rejected options, later runtime heuristics will naturally create deadlocks. `CLAUDE.md` already notes that belief quality matters more than runtime fixes. 

### `simulator.py`

This module is currently both a realizer and a behavior controller. That is too much responsibility. It should primarily realize a planned dialogue act in a persona voice.

Right now, `simulator.py` contains important behavior logic: phase-specific instructions, narrowing instructions, position discipline, forced adaptation, skepticism nudges, repetition avoidance, and openers. The simulator prompt includes participant identity, backstory, goal, personality summary, private belief block, topic, all options, recent conversation, own recent points, phase, turn instruction, interaction instruction, position discipline, skepticism nudge, forbidden openers, and opener constraints. 

This explains much of the token cost. Every turn resends stable information that should be cached, compressed, or represented as a short speaker card.

Also, some LLM-facing text is not centralized in `prompts.py`. For example, `simulator.py` builds phase instructions and narrowing instructions before passing them into `prompts.sim_turn`. Since these strings are part of the LLM prompt, they violate your hard requirement that all prompts sent to the LLM live in `prompts.py`.

### `turn_manager.py`

The current turn manager is a reasonable heuristic prototype. It captures several important intuitions: direct address should matter, pending questions should matter, extraversion affects speaking probability, recent speakers should be penalized, and repeated speakers should be suppressed. 

But it is not yet theoretically grounded enough. Sacks/Schegloff/Jefferson do not describe turn-taking as “weighted random speaker choice.” Their model gives an ordered mechanism at transition relevance places: if the current speaker selects a next speaker, that selected participant has the right and obligation to speak; if no next speaker is selected, self-selection may occur; if no one self-selects, the current speaker may continue. The current `TurnManager` approximates only the first part and does not explicitly model self-selection, current-speaker continuation, transition points, or unresolved adjacency obligations. 

### `consensus.py`

The current consensus detector has useful tiers, but it is too string-based. It checks agreement language, regex votes, reduced opposition, and LLM fallback. 

The reduced-opposition tier is the closest to Fisher: it treats emergence as plurality support plus dissenters becoming ambiguous rather than actively objecting. 

The problem is that ambiguity is not actually represented as a first-class state. It is inferred by absence of objection strings. That is weaker than Fisher’s model. Fisher distinguishes favorable, unfavorable, and ambiguous units toward decision proposals and describes phase progression as changing proportions of those units over time. 

A stronger implementation would explicitly classify each participant utterance toward each option as `support`, `oppose`, `ambiguous`, `conditional_support`, `neutral`, or `blocker`.

### `moderation.py`

The moderation engine has useful concepts: escalation levels, narrowing, stuck loop detection, outlier handling, compromise testing, and force-close avoidance. It also aligns with the project rule that compromise should be tested before force-close. 

However, it is heavily heuristic and threshold-based. Some thresholds are in config, but others are embedded in code. The module also uses string-level detection for speculative loops and outliers. This should be replaced or supplemented by dialogue-act and stance tracking.

### `prompts.py`

This file is a strong foundation. It contains option generation, role assignment, persona generation, belief generation, simulator turn prompt, consensus check, and moderator prompt functions. 

The main issue is incomplete centralization. Prompt fragments are still built in other modules. You need to define prompt builders that accept structured objects:

`build_sim_turn_prompt(turn_plan, speaker_card, public_state, local_context)`
`build_stance_classifier_prompt(turn_text, options)`
`build_moderator_prompt(intervention_plan, public_state)`
`build_persona_group_prompt(topic, names, options, traits)`.

The prompt text itself should live only in `prompts.py`.

### `llm_client.py`

The provider abstraction is good. Token counters are also useful. 

The next step is component-level token accounting. For each LLM call, log:

prompt type, module, participant, phase, tokens in, tokens out, stable-context tokens, recent-history tokens, options tokens, persona tokens, instruction tokens.

This lets you identify whether token waste comes from persona blocks, full option blocks, repeated recent history, moderator calls, consensus calls, or setup calls.

### `logger.py`

The logger writes useful files, but it should become the backbone of evaluation. Current CSV rows do not capture enough state. 

Add JSONL traces with the full decision record per turn. The human transcript should stay clean, but the machine trace should include everything needed to debug why the system selected a speaker, why a phase changed, why consensus was accepted/rejected, and why force-close happened.

### `utils.py`

Useful helper file, but too much depends on regex extraction. Regex is fine for a first pass, but it cannot carry the scientific model. Use it as a fast deterministic classifier, then only call an LLM classifier for ambiguous cases.

## 5. What the Provided Papers Contribute

### Fisher — Decision Emergence

Fisher’s main contribution for your project is not just “four phases.” It is the idea that group decisions emerge from interaction patterns over time. The decision is not merely an endpoint; it is visible in changing verbal evidence toward decision proposals. Fisher explicitly frames the study around interaction process rather than only product/outcome. 

The useful implementation model is:

Orientation: tentative exploration. Clarification and agreement are common, but early agreement may function socially rather than as true decision commitment. Ambiguous comments are frequent. 

Conflict: unfavorable statements rise. Alternatives are challenged, resisted, compared, and refined.

Emergence: unfavorable statements decline and ambiguous statements rise relative to unfavorable ones. This is the important part for your simulator. Softening, conditional acceptance, hedging, and “I could live with that if…” are not noise. They are evidence that dissent is dissipating.

Reinforcement: favorable statements dominate, ambiguous and unfavorable statements decline sharply, and the group reinforces the emerging decision. Fisher describes the final phase as marked by favorable attitudes receiving positive reinforcement and dissent virtually vanishing. 

Implementation implication: do not detect consensus only from explicit votes. Detect a candidate option moving through conflict → emergence → reinforcement. That requires tracking per-option favorable, unfavorable, and ambiguous evidence over a rolling window.

Important caveat: Fisher’s model should not be treated as a deterministic script. Fisher explicitly says the four phases are not necessarily present in all task groups and that phase progression is gradual rather than sharply discrete. 

### Sacks, Schegloff & Jefferson — Turn-Taking

The useful part for your simulator is the ordered turn-allocation mechanism.

At a transition point, the rules are roughly:

If the current speaker selects a next speaker, the selected speaker has priority and obligation to speak next.
If no next speaker is selected, another participant may self-select.
If nobody self-selects, the current speaker may continue.
The rules reapply recursively at subsequent transition points. 

Implementation implication: `TurnManager` should not only compute weighted speaker probabilities. It should first resolve obligations:

direct question to X → X should answer;
explicit mention of X → X has high response priority;
open question to group → self-selection among relevant participants;
no obligation → self-selection based on participation debt, personality, and act utility;
no self-selection → possible moderator or current-speaker continuation.

This maps directly to your problem: realistic group chat depends on who was selected, who self-selects, who owes an answer, and who has already spoken too much.

### MUCA — Multi-User Chat Assistant

MUCA contributes the cleanest architecture vocabulary: multi-user conversation requires controlling three dimensions, not one: What to say, When to respond, and Who to answer. The paper explicitly contrasts this with single-user chatbots that mainly decide what to answer. 

MUCA’s framework also matters structurally. It uses a Sub-topic Generator, Dialog Analyzer, and Conversational Strategies Arbitrator. Its diagram includes subtopic status, utterance feature extraction, accumulative summary, participant features, and strategies such as keep silent, direct chatting, participation encouragement, conflict resolution, and initiative summarization. 

Implementation implication: split your simulator loop into:

When: should anyone speak now, and who has obligation?
Who: who is addressed or replied to?
What: what dialogue act should be performed?
How: realize the planned act in persona voice.

Right now, these are mixed across `turn_manager.py`, `simulator.py`, `moderation.py`, and `orchestrator.py`.

MUCA also discusses compute cost and short utterance generation difficulties for LLM-based multi-user simulation. It notes that LLM simulators may repeat conversational strategies and that cooldown mechanisms can help. 

Implementation implication: strategy cooldowns should be explicit state, not only forbidden openers.

### Ouchi & Tsuboi — Addressee and Response Selection

This paper is directly relevant to your addressee problem. It formalizes multi-party conversation as selecting both addressee and response. The key challenge is jointly modeling who is talking about what at each time step. 

The paper also shows why addressee tracking matters especially in text chat: unlike face-to-face conversation, text often uses explicit name mentions or user IDs to indicate addressee. 

Implementation implication: every generated turn should store:

speaker,
addressee or addressees,
reply-to turn id,
topic/thread,
dialogue act,
option stance.

The paper’s experimental setup uses context windows of 5, 10, and 15 utterances and truncates utterances to 20 words for efficiency. 

Implementation implication: your per-turn prompt should not blindly include large history windows. Use short local context plus structured long-term state.

### McCrae & John — Five-Factor Model

McCrae & John define the Five-Factor Model as a hierarchical organization of traits in terms of Extraversion, Agreeableness, Conscientiousness, Neuroticism, and Openness to Experience. They describe these as broad dimensions of enduring emotional, interpersonal, experiential, attitudinal, and motivational styles. 

The paper is useful as a justification for using the Big Five as a broad trait framework, not as a direct algorithm for dialogue behavior. It supports the idea that the Big Five are broad individual-difference dimensions, but your mapping from traits to speaking probabilities, compromise behavior, emotional tone, and disagreement style is an engineering design decision.

Engineering inference: traits should bias probabilities and style, not deterministically produce behavior. Low agreeableness should increase direct disagreement and reduce automatic validation. It should not automatically create a hard blocker. High neuroticism should increase risk salience and anxious framing. It should not automatically create refusal. High extraversion should increase speaking probability and reactive turns. High conscientiousness should increase detail orientation and stable criteria. High openness should increase reframing and alternative exploration.

## 6. Main Failure Modes

### 1. Too many stubborn simulations

Your intended target is plausible rare hard blocking, perhaps 0–10% of dialogues. The current design likely produces too many blockers because several independent mechanisms all push toward resistance.

Low agreeableness can make participants challenging. High neuroticism can make them risk-focused. The belief generator can assign narrow acceptable sets and rejected options. `simulator.py` adds skepticism nudges for low agreeableness or high neuroticism. Emergence logic can tell participants to name remaining concerns. Consensus logic may treat one dissenter as acceptable for majority but confirmation then reactivates the dissenter. The combined effect is far stronger than any single rule.

### 2. Consensus detection is under-modeled

Current consensus detection relies on soft phrase lists, regex votes, reduced opposition, and LLM fallback. 

The missing part is explicit public stance state. You need to know:

Who supports which option?
Who opposes which option?
Who conditionally accepts which option?
Who is ambiguous?
Which objections are unresolved?
Which conditions have been addressed?
Which option is emerging?

Without this, consensus is either premature or delayed until force-close.

### 3. Turn-taking is plausible but not interactionally grounded

The current turn manager uses weighted scores. That works sometimes, but it does not properly represent selected next speaker, self-selection, current-speaker continuation, adjacency pairs, or open obligations.

The result is that sims may ignore direct references, answer too late, respond to the wrong person, or continue with generic option talk when the local conversational structure demands an answer.

### 4. Prompt/token inefficiency

The current per-turn prompt repeats stable information: topic, options, backstory, goal, personality summary, private beliefs, style rules, recent history, own recent points, phase instructions, interaction instructions, and constraints. The persona pipeline itself also uses multiple setup calls per participant: role assignment, persona concept generation, and belief generation. 

This explains the reported ratio of roughly 60k input tokens to 3k output tokens. The system is paying repeatedly for context that should be cached or compressed.

### 5. Chats can feel scripted

The system repeatedly gives the LLM similar instructions: react, answer, do not repeat, name a condition, state preference, avoid vague questions. This creates structural repetition. The surface phrases may vary, but the move structure stays similar.

The better fix is a dialogue-act planner that explicitly varies moves: answer, challenge, clarify, concede, conditionally accept, ask a targeted question, summarize, propose compromise, confirm, reject with blocker, or stay silent.

### 6. Invented facts

`CLAUDE.md` already identifies made-up attributes as an issue. 

The prompt says options are the only shared facts, but this is not enforced structurally. You need either a deterministic option-fact checker or a post-generation repair step that flags claims not grounded in option text.

## 7. Root Causes

The main root cause is that the current system uses raw transcript strings as the primary memory. This causes multiple downstream weaknesses.

Consensus is inferred from text rather than stored as stance evolution.
Turn-taking is inferred from recent mentions rather than stored as obligations.
Phase progression is procedural rather than evidence-driven.
Moderation responds to symptoms such as repetition pressure rather than a precise state such as “Casey has an unresolved blocker against Option B.”
Prompting compensates for missing state by repeating many instructions.
LLM behavior becomes uncontrolled because each turn prompt asks the model to infer too much.

The second root cause is that personality and stubbornness are entangled. Big Five traits should shape style and tendencies. They should not frequently create hard refusal. Hard refusal should be explicitly sampled, capped, and logged.

The third root cause is magic-number dispersion. Even though `config.yaml` exists, many behavior-changing values are still embedded in code. This makes experiments hard. You cannot easily say “I reduced hard blockers from 60% to 8%” if the relevant causes are spread across sampling, belief generation, skepticism nudges, emergence prompts, consensus thresholds, and force-close scoring.

The fourth root cause is that LLM calls are used where deterministic state logic would be better. LLMs are useful for natural language realization, option generation, persona text, and ambiguous classification. They are weaker and more expensive for repeated state reconstruction.

## 8. Target Architecture

The target architecture should be refactored around structured state and a planning-realization split.

Recommended module structure:

`dialogue_state.py`
Defines core dataclasses.

`state_tracker.py`
Updates structured state after every turn.

`turn_policy.py`
Chooses next speaker(s) and addressee obligations.

`act_planner.py`
Chooses what kind of move the selected speaker should make.

`prompts.py`
Contains every LLM-facing template and prompt fragment.

`realizer.py`
Calls the LLM to realize a planned move in the selected persona’s voice.

`consensus_engine.py`
Tracks support, opposition, ambiguity, conditional acceptance, blockers, and consensus.

`phase_detector.py`
Detects Fisher-style phase based on stance evidence trends.

`moderator_policy.py`
Chooses moderator interventions and escalation.

`token_manager.py` or `prompt_context.py`
Builds compact context windows and summaries.

`metrics.py` / `evaluate_logs.py`
Computes batch metrics.

`logger.py`
Writes transcript plus full JSONL trace.

A minimal `TurnRecord` should store:

```python
turn_id: int
speaker: str
text: str
phase: str
is_moderator: bool
addressees: list[str]
reply_to: int | None
dialogue_act: str
option_stances: dict[str, str]
mentioned_options: list[str]
is_question: bool
answers_question_id: int | None
selected_reason: str
tokens_in: int
tokens_out: int
prompt_type: str
```

A minimal `ParticipantState` should store:

```python
name: str
persona: Persona
public_preference: str | None
public_stances: dict[str, str]
conditions: dict[str, str]
hard_blockers: dict[str, str]
turn_count: int
last_spoke_turn: int | None
participation_debt: float
open_questions_to_answer: list[int]
recent_dialogue_acts: list[str]
strategy_cooldowns: dict[str, int]
is_hard_blocker: bool
```

A minimal `OptionState` should store:

```python
option_id: str
supporters: set[str]
opponents: set[str]
ambiguous: set[str]
conditional_supporters: dict[str, str]
hard_blockers: dict[str, str]
last_mentioned_turn: int
support_score: float
opposition_score: float
```

A minimal `PhaseEvidence` should store:

```python
phase: Literal["orientation", "conflict", "emergence", "reinforcement"]
confidence: float
window_support_rate: float
window_oppose_rate: float
window_ambiguous_rate: float
window_conditional_rate: float
trend_support: float
trend_oppose: float
trend_ambiguous: float
```

This target architecture directly maps to the papers:

Fisher gives phase and stance evidence.
Sacks/Schegloff/Jefferson give ordered turn-allocation rules.
MUCA gives What/When/Who separation.
Ouchi & Tsuboi justify explicit addressee/reply tracking.
McCrae & John justify broad trait dimensions, while the probabilistic behavior mapping remains your engineering design.

### Stage 5: Turn-Taking Redesign

### Stage 6: Big Five Behavior Redesign

Separate three things:

Personality traits: stable broad tendencies.
Dialogue role/state: current obligations and public stance.
Hard blocking: rare latent behavior state.

Trait effects should be probabilistic:

Openness: increases reframing, alternative exploration, and willingness to consider novel compromise.
Conscientiousness: increases criteria-based reasoning, consistency, and reluctance to flip without evidence.
Extraversion: increases self-selection probability, reaction frequency, and longer turns.
Agreeableness: increases softening, validation, compromise probability, and reduced face-threatening disagreement.
Neuroticism: increases risk salience, worry language, and sensitivity to unresolved uncertainty.

Hard blocker design:

Sample at dialogue level, not participant level.
Config: `hard_blocker_dialogue_probability`, target 0.0–0.10.
Config: `max_hard_blockers = 1`.
A hard blocker must have a clear public reason.
A hard blocker can still accept a compromise if their stated blocker condition is met.
Low agreeableness alone never implies hard blocking.

### Stage 7: Consensus and Phase Redesign

Use Fisher as the core model.

Each turn updates option-level evidence:

`support`
`oppose`
`ambiguous`
`conditional_support`
`blocker`
`neutral`.

Phase detector:

Orientation: many neutral/ambiguous/clarification acts, low strong opposition.
Conflict: opposition and challenge acts rise.
Emergence: opposition declines; ambiguous and conditional support increase around one candidate.
Reinforcement: explicit support/confirmation dominates; opposition and ambiguity are low.

Consensus detector:

A candidate can be “emerging” before it is final.
A candidate is final only if visible support threshold is reached, no unresolved hard blocker remains, and conditions are either accepted or minor.
A 2-vs-1 majority in a 3-person group should usually be “majority candidate,” not full consensus, unless the dissenter has softened to conditional acceptance.
Confirmation should test public acceptance, not private belief compatibility.

LLM fallback should classify ambiguous stances, not replace deterministic state.

## 13. Token Efficiency Plan

The current token problem is structural. The simulator repeatedly sends stable information. The setup also uses multiple per-participant calls. 

Priority changes:

First, combine setup calls. Generate all participant profiles in one group prompt. Generate all beliefs in one group prompt. This alone can save repeated topic/options/context tokens.

# Master Plan: Scientifically Grounded Multi-Party Dialogue Simulator

## 1. Core Diagnosis

Your current architecture is a strong prototype, not a broken system. The major components are already present: `Orchestrator`, `PersonaBuilder`, `Simulator`, `TurnManager`, `ConsensusDetector`, `ModerationEngine`, `DialogueLogger`, `LLMClient`, config loading, and a centralized `prompts.py` direction. `CLAUDE.md` also shows that the intended design is already clear: controlled decision dialogue with stable personas, grounded disagreement, answer obligations, compromise testing, varied message length, and non-scripted progression. 

The main weakness is that the system still treats the transcript as the source of truth. Many things are recomputed from `list[str]` history: votes, addressees, pending questions, repeated points, current leading option, consensus, and phase evidence. That produces brittle regex logic, repeated prompt instructions, expensive context windows, and uncontrolled LLM behavior.

The correct target is not “better prompts only.” The correct target is:

state tracking → turn/addressee selection → dialogue-act planning → compact LLM realization → stance update → phase/consensus update → moderator policy → logging/evaluation.

The LLM should mostly produce natural wording for a planned conversational move. It should not repeatedly infer the whole group state from raw chat history.

## 2. Best New Insights from the Other Response

The other response adds these important points:

First, the **confirmation rejection path** deserves special attention. A single rejection during confirmation can reset the agreement state, reopen discussion, send priority back to the rejecting speaker, and often trigger another failed confirmation. This should become a measured failure mode: `confirmation_rejection_count`, `same_candidate_retested`, `reopened_after_confirmation`, and `force_closed_after_confirmation_failure`. 

Second, the system should distinguish **visible public stance** from **private belief state** more strictly. Private `AgentBeliefs` are useful for generating coherent persona behavior, but final consensus and force-close should be justified from public dialogue evidence. This matches your own project goal: the transcript must make the outcome defensible.

Third, the response correctly identifies that Fisher-style “emergence” should not merely mean “everyone voted and no regex consensus was found.” Fisher’s useful signal is the changing pattern of favorable, unfavorable, and ambiguous statements over time. The current `ConsensusDetector` has a “reduced opposition” tier, but it is still not a proper stance-evidence model. 

Fourth, the response is right that refactoring should be staged by running new structured state **in parallel** first. Do not rip out the old detector immediately. Add `TurnRecord`, `StanceTable`, and `DiscourseGraph`, populate them during each turn, log both old and new decisions, and compare.

Fifth, it gives a useful practical token insight: a large amount of input cost comes from resending stable context every simulator turn: persona, options, voice/style rules, beliefs, repeated constraints, and recent history. The current `PersonaBuilder` pipeline also documents setup as `2N + 2` LLM calls per dialogue: options, roles, N persona concepts, and N belief generations.

## 3. Important Problems in the Other Response

Do not adopt these parts uncritically.

The statement “prompt construction is entirely in `prompts.py`” is too optimistic. `prompts.py` is the main prompt registry, but `simulator.py` still builds LLM-facing behavioral strings. For your requirement, those strings must move into `prompts.py`.  

The proposed hard rule “after N blocking turns, force concession” is risky. It can produce exactly the kind of fake consensus you want to avoid. Replace it with a sampled, logged, rare hard-blocker model and condition-based softening.

The proposed Fisher transition rule “orientation → conflict when unfavorable exceeds ambiguity; conflict → emergence when ambiguity exceeds unfavorable” is too mechanical. Fisher’s phases are useful as evidence trends, not exact thresholds. Use rolling evidence and confidence, not one hard phase switch.

“Cached system message” is not equally available across Gemini, Groq, and your university endpoint. You can still split stable and dynamic prompt components, but do not assume real provider-side prompt caching. Treat caching as an optional optimization. The portable improvement is prompt compression, not API caching.

The recommendation to remove fallback options entirely is too strong. Better: add config modes. In development, fail fast if option generation fails. In batch production, optionally use fallback but log `option_generation_failed=true`. Silent fallback is bad; explicit fallback is acceptable.

The suggested target `force_close_rate ≤ 30%` may be too high or too low depending on topic type and participant count. Use it as an initial diagnostic, not a scientific target. More meaningful: true hard-blocker dialogue rate should be near your design target, for example 0–10%, while force-close should be explainable from public stance evidence.

## 6. Paper Mapping into Implementation

| Paper / Concept                                         | Implementation meaning                                                                            | Concrete module change                                   |
| ------------------------------------------------------- | ------------------------------------------------------------------------------------------------- | -------------------------------------------------------- |
| Fisher: favorable / unfavorable / ambiguous statements  | Track stance evidence per option and participant                                                  | `stance_tracker.py`, `phase_detector.py`, `consensus.py` |
| Fisher: emergence                                       | Detect softening: opposition decreases, ambiguity/conditional support increases                   | `phase_detector.py`                                      |
| Fisher: reinforcement                                   | Closure only after visible support dominates and unresolved blockers are gone                     | `consensus.py`, `moderation.py`                          |
| Sacks/Schegloff/Jefferson: selected next speaker        | Direct questions and address terms create response obligations                                    | `turn_policy.py`, `DiscourseGraph`                       |
| Sacks/Schegloff/Jefferson: self-selection               | If no one is selected, participants self-select based on relevance/personality/participation debt | `turn_policy.py`                                         |
| Sacks/Schegloff/Jefferson: current speaker continuation | Rare continuation if no other speaker has priority                                                | `turn_policy.py`                                         |
| MUCA: What / When / Who                                 | Separate act planning, turn timing, addressee selection                                           | `act_planner.py`, `turn_policy.py`                       |
| MUCA: dialog analyzer                                   | Periodically update public state, topic/option status, participant features                       | `state_tracker.py`                                       |
| Ouchi & Tsuboi: addressee-response selection            | Every turn needs addressee and reply-to metadata                                                  | `TurnRecord`, `DiscourseGraph`                           |
| McCrae & John: Big Five as broad traits                 | Traits bias probabilities and style, not scripted phrases                                         | `persona.py`, `act_planner.py`, `turn_policy.py`         |

Fisher gives your phase and consensus evidence model. Sacks/Schegloff/Jefferson gives your turn-allocation rule cascade. MUCA gives your architectural separation of What/When/Who. Ouchi & Tsuboi gives your addressee/reply-to representation. McCrae & John justifies the Big Five trait framework, but the exact mapping from traits to simulator behavior is your engineering design.

### Stage 3 — Prompt Centralization

Move all LLM-facing text into `prompts.py`.

This includes text currently built in `simulator.py`:

narrowing instructions, phase instructions, interaction instructions, position discipline, skepticism nudges, forced adaptation text, forbidden opener wording, closure instructions if LLM-facing.

After this stage, other modules may pass structured values, but they must not assemble prompt prose.

Bad:

```python
instruction = "You are the remaining holdout. Name your concrete dealbreaker..."
```

Good:

```python
prompt = prompts.sim_turn(
    speaker=speaker_card,
    turn_plan=turn_plan,
    state=public_state,
    context=local_context,
)
```

Inside `prompts.py`, build the prose.

### Stage 4 — Prompt/Token Compression

Separate stable and dynamic context.

Stable per dialogue/persona:

topic, options, persona name, role, compact backstory, goal, Big Five summary, private beliefs, allowed known facts.

Dynamic per turn:

phase, current act plan, addressee/reply target, relevant options only, last 4–6 turns, unresolved question/condition, public stance summary.

Do not resend full stable blocks as large free text if a compact speaker card is enough.

Target prompt shape:

```text
Speaker card:
- Riley, primary traveler
- reserved, practical, short turns
- prefers B; can accept C if cost is handled

Current public state:
- Candidate: B
- Casey supports B
- Blake conditionally accepts B if timing is clear
- Riley has unresolved concern: baggage fee

Your planned act:
Answer Blake directly and state whether B is acceptable if the fee is included.

Recent context:
...
```

This is more controllable than a long “be natural, avoid repetition, remember your personality, follow your beliefs” prompt.

### Stage 5 — Dialogue State Redesign

Add the new state objects and populate them in parallel with old logic.

At first, do not use the new state for decisions. Just log it and compare.

`state_tracker.py` should parse each new turn once and update:

speaker, addressee, reply-to, dialogue act, mentioned options, stance updates, question obligations, answered questions, preference changes, blockers, conditions.

The old `history: list[str]` can remain for transcript output, but the new logic should gradually migrate to `state.turns`.

### Stage 6 — Turn-Taking Redesign

Replace pure weighted speaker selection with a rule cascade.

Order:

1. Direct question to named participant → that participant has first priority.
2. Direct mention or challenge → addressed participant has high priority.
3. Open group question → self-selection among relevant participants.
4. No obligation → self-selection based on participation debt, phase need, personality, and stance relevance.
5. No useful participant move → moderator may intervene.
6. Rarely, current speaker may continue.

This keeps Sacks/Schegloff/Jefferson as the theoretical basis while still using probabilities for natural variation.

Keep old `TurnManager` behind a config flag for A/B testing.

### Stage 7 — Dialogue-Act Planner

Add `act_planner.py`.

Before the LLM writes a turn, choose the intended act:

`GREET`, `OPEN_PRIORITY`, `ASSERT_SUPPORT`, `ASSERT_OPPOSITION`, `ASK_CLARIFICATION`, `ANSWER`, `CHALLENGE`, `CONCEDE`, `CONDITIONAL_ACCEPT`, `PROPOSE_COMPROMISE`, `COMMIT_VOTE`, `CONFIRM`, `REJECT_WITH_REASON`, `GOODBYE`, `SILENCE`.

The LLM receives one act plan, not a pile of competing instructions.

Example:

```python
TurnPlan(
    speaker="Riley",
    addressee="Blake",
    reply_to=17,
    act="CONDITIONAL_ACCEPT",
    target_option="B",
    condition="only if baggage fee is included",
    max_words=32,
)
```

This will reduce scriptedness because the structure varies explicitly.

### Stage 8 — Big Five Redesign

Keep Big Five traits, but remove caricature phrases.

Traits should affect probabilities:

Openness:
more reframing, more alternative exploration, more willingness to consider unusual compromise.

Conscientiousness:
more criteria-based reasoning, more consistency, less random vote flipping, more concern about missing details.

Extraversion:
higher self-selection probability, more reactions, slightly longer turns.

Agreeableness:
more validation, more softening, more compromise, less direct face-threatening disagreement.

Neuroticism:
more risk salience, more worry, more sensitivity to unresolved uncertainty.

Do not map:

low agreeableness → hard blocker
high neuroticism → hard blocker
high conscientiousness → never changes mind

Add explicit rare hard-blocker sampling:

```yaml
stubbornness:
  hard_blocker_dialogue_probability: 0.05
  max_hard_blockers_per_dialogue: 1
  require_public_reason: true
  allow_softening_if_condition_met: true
```

A blocker should have a condition or concrete reason. If the condition is addressed, they may soften. If not, failure is plausible.

### Stage 9 — Consensus and Phase Redesign

Replace “vote counting plus fallback” with stance evidence.

Each option has public stance evidence:

support, opposition, ambiguity, conditional support, blockers.

Fisher phase evidence:

Orientation:
many neutral/ambiguous/clarification turns, low strong opposition.

Conflict:
opposition and challenge increase.

Emergence:
opposition decreases, ambiguity and conditional support increase around one candidate.

Reinforcement:
support/confirmation dominates, opposition is low, conditions are resolved or accepted.

Consensus states:

`none`
`candidate_emerging`
`majority_candidate`
`conditional_consensus`
`full_consensus`
`blocked`
`failed`.

Closure requires:

visible support or conditional support from all/most participants depending on config, no unresolved hard blocker, and confirmation not contradicted by public stances.

Force-close should be renamed conceptually to something like `best_available_decision` and should be explicitly logged as non-consensus.

### Stage 10 — Moderator Redesign

Moderator policy should act on structured state.

Interventions:

clarify unresolved condition, ask addressed participant to answer, ask holdout for concrete blocker, summarize emerging candidate, test compromise, invite backup option, confirm decision, declare failure/no consensus.

Avoid generic “can we agree?” prompts if the state says the actual issue is one participant’s unresolved condition.

The moderator should not force closure merely because rounds passed. It should force or fail only when:

max rounds reached, no stance movement, repeated unresolved blocker, or no candidate has enough support.

### Stage 11 — Grounding / Fact Control

Add `KNOWN_FACTS`.

The options generated by the moderator are the shared factual ground. Persona backstory may explain preferences, but it must not invent facts about the current options.

Post-turn validator:

Check whether a generated turn asserts concrete attributes not present in option text or previous public dialogue. If yes, repair once.

Use deterministic checks first. Use LLM fact-check only for ambiguous cases, because LLM fact-checking adds cost.

### Stage 12 — Evaluation

Create a fixed `eval_scenarios.txt`.

Run current baseline first. Then after each stage, run the same topics with fixed seeds.

Quantitative metrics:

force-close rate, true hard-blocker rate, consensus success rate, confirmation rollback rate, question-answer rate, addressee response rate, phase progression, participation Gini, top-speaker fraction, repetition rate, invented-fact rate, vote-flip rate, token cost per dialogue, token cost per successful dialogue.

Qualitative rubric:

naturalness, coherence, human-likeness, local reply correctness, disagreement plausibility, compromise plausibility, ending quality, persona distinctiveness, topic grounding.
