## What is good now

The biggest improvement is macro-structure. The dialogues now usually have an opening, initial preference statements, challenge/response turns, compromise attempts, final vote/acceptance, and a closing. That is much closer to an actual group-decision shape than short preference dumps.

The “known context” is being used. Participants refer to concrete constraints: budget, group size, travel time, preparation time, deadline, study duration, player count, available space, etc. For example, the cafe run uses the 5-hour study duration; the potluck run uses the 20 guests and $50 budget; the software framework run uses the 6-month deadline and team size. This is a strong direction because it makes the discussion more grounded.

The practical-constraint acts are also visibly present. People ask about seating, menu options, reviews, cost, serving size, preparation effort, parking, installation, lyrics, reservations, and rules. That is socially useful because real group decisions are rarely only “I like A, you like B.” They usually become “Can we afford it?”, “Will everyone fit?”, “Can beginners handle it?”, “Who books it?”, “Does it work with the time window?”

The moderator is less intrusive than before. Moderator ratio is mostly around 6–14%, which is acceptable. The participants carry most of the discussion. That is better than having the moderator drive everything.

There is also some real disagreement. The software framework run remains unresolved because Daria does not truly accept React/Redux. That is good. The generator did not force fake consensus there. The playlist run ends as fallback with only 0.75 support, which is also socially plausible.

## Main problems

The third issue is invented context. The model often adds factual claims that were not in the options or known context. Examples:

In the cafe run, someone claims The Daily Grind has “a big table in the back,” “happy hour,” and is “less crowded than The Quiet.” None of that is given.

In the restaurant run, someone claims Sakura has tight tables and possibly reservation behavior.

In the road trip run, someone estimates fuel costs for combining routes.

In the hiking run, the dialogue starts discussing parking, crowd size, narrowness, and group-fit beyond what is reliably given.

This is dangerous for your simulator goal. The system should distinguish between known facts and uncertainty. Natural dialogue may say “we should check whether they have a big table,” but it should not say “they have a big table in the back” unless that was given.

The fourth issue is weak adjacency. People ask questions, but the next turn often does not answer the question directly. Sometimes another participant shifts the topic. Sometimes the moderator asks the wrong person or frames the issue incorrectly. Example: in the framework run, the moderator asks Wyatt what needs to change about React for his scalability concerns, but Wyatt already supports React for scalability. The actual unresolved concern is Daria’s maintainability objection. That moderator prompt is logically wrong.

The fifth issue is premature or under-justified consensus. The final decision often happens after one or two reluctant acceptance turns, but the underlying concern is not fully resolved. In the board game run, Settlers of Catan wins despite the option itself saying it works best for 3–4 players, while the dialogue has 7 participants. Codenames is barely discussed even though it is the obvious large-group candidate. In the potluck run, Grilled Chicken Skewers win despite “varied dietary needs,” while the vegetarian issue is only patched with a side dish. These are not impossible choices, but the reasoning is too thin for a real group.


## Social realism issues

The closings are also too uniform. Many runs end with “later,” “catch you later,” “see ya,” “X it is.” That creates a repeated closing ritual. It is not wrong once, but across 15 logs it becomes visible.

The participants still lack stable social identities. Their roles/traits affect preference, but not voice. A cautious person, a joking person, a practical planner, and an enthusiast all use similar syntax. The persona system controls what they support, but not enough how they speak.

There is also too little social memory. People rarely refer back naturally: “you said earlier…”, “I’m okay with that if…”, “that solves my concern,” “I still need one thing clarified.” Instead, they mostly restate option attributes. This makes the dialogue feel like parallel argument generation rather than a group jointly managing common ground.

The compromise moves are present but too mechanical. “Combine A and B” appears often. Sometimes that is useful, but sometimes it creates invalid hybrid options. In the framework run, “React with strict type checking and some Angular principles” is not a clean option. In the space-station run, merging meditation with zero-gravity sports sounds creative but needs safety/space reasoning. The generator should only allow hybrids if the topic type supports configurable combinations.

## What needs to be fixed first

Priority 1: Fix option-name handling. No clipped names. Store each option with a short alias and a full display name. For example:

Full: “Settlers of Catan”

Alias: “Catan”

Never produce “Settlers of.” For long names, define allowed aliases during setup.

Priority 2: Add a strict known/unknown distinction. The model may say “we should check if The Daily Grind has a big table.” It may not say “they have a big table” unless that fact is in known context. This one change would remove many hallucination-like defects.

Priority 3: Improve adjacency-pair control. If a turn asks a question to Pavel, the next selected speaker should usually be Pavel, and the act should be answer/clarify/refuse, not introduce a new option. Add controller state like:

open_question: target speaker, topic, required answer type

Then route the next turn to close that question before moving on.

Priority 4: Add concern-resolution tracking. A participant should not accept unless their main concern is explicitly solved, softened, or traded off. For example:

Concern: “Catan only supports 3–4 players.”

Valid resolution: “We can split into two tables,” “we have the expansion,” or “we reject Catan.”

Invalid resolution: “Catan has good negotiation.”

Priority 6: Reduce phrase-template repetition. Do not let the same act always surface as the same wording. The act can be fixed internally, but the realization should vary. For example, instead of repeatedly generating “What if…”, allow:

“Could we handle that by…”

“One workaround is…”

“That only works for me if…”

“I’d be more comfortable if…”

“That solves part of it, but…”

Priority 7: Separate decision types. Some topics require choosing one fixed option. Others allow modification. A restaurant choice can include “check menu” or “book table,” but the restaurant itself stays fixed. A playlist can be blended. A software architecture can combine frontend/backend choices, but only if the options are modeled as components. Without this distinction, the simulator invents hybrids too freely.

## Most important diagnosis

Your generator is now good at producing decision-shaped conversations. It is not yet good at producing socially situated conversations.

The current logs have structure, length, disagreement, and outcomes. That is progress. The remaining failures are mainly: surface template repetition, invented facts, weak response-to-previous-turn logic, and shallow concern resolution.

The next improvement should not be “add more personality” in a broad sense. It should be tighter dialogue-state control: who asked what, who owes an answer, which concern is unresolved, which facts are known, which options have been eliminated, and whether a compromise is actually valid. Once that state is cleaner, persona voice variation will matter much more.
